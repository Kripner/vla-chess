# SO-101 arm description (the single source of truth)

Vendored SO-101 model. Every representation derives from this one description: `arm/so101_kin.py`
parses `so101.urdf` at import for FK, and the MuJoCo scene (`chess/sim/scene.py`) loads `so101.xml`,
the same chain (checked by an FK-parity smoke).

## Provenance
- Generated by [onshape-to-robot](https://github.com/Rhoban/onshape-to-robot) from the
  Onshape CAD model, via the [SO-ARM100](https://github.com/TheRobotStudio/SO-ARM100) repo
  (`Simulation/SO101/so101_new_calib.{urdf,xml}`). Onshape doc:
  `cad.onshape.com/documents/7715cc284bb430fe6dab4ffd`.
- **new_calib**: each joint's virtual zero is the **midpoint of its range** — which matches
  our existing `offset = MJCF range midpoint` convention, so the tick calibration carries over.

## Files
- `so101.urdf` — the FK/geometry source of truth (parsed by `arm/so101_kin.py`).
- `so101.xml` — MuJoCo MJCF (same chain; also carries the STS3215 servo dynamics:
  `damping 0.60, frictionloss 0.052, armature 0.028, kp 998.22, forcerange ±2.94` — reference
  for a dynamics calibration).
- `assets/*.stl` — per-link meshes (paths are relative: `assets/<name>.stl`).

## Chain (base → tip), all joint axes `[0,0,1]`
`base_link → shoulder_link → upper_arm_link → lower_arm_link → wrist_link → gripper_link
→ moving_jaw_so101_v1_link`; fixed `gripper_frame_link` (TCP) hangs off `gripper_link`.
Joint ranges (rad): pan ±1.9199, lift ±1.7453, elbow ±1.69, wrist_flex ±1.6581,
wrist_roll −2.7438..2.8412, gripper −0.1745..1.7453.

## Notes
- Upstream flagged the base **collision** meshes as problematic in sim; the sim uses its own
  collision geometry (`so101.xml`).
- LeRobot exposes the gripper as a linear 0–100 (0=closed, 100=open); here it is the revolute
  `gripper` joint — the 0–100 ↔ angle map lives in `arm/mapping.py`.

## Jaw collision decomposition
MuJoCo collides a mesh geom by its **convex hull**, and both grasping parts are hooked: a single
hull is 2.33x (`moving_jaw_so101_v1`) / 2.58x (`wrist_roll_follower_so101_v1`) the true volume and
fills the gripper mouth, so the arm grasps through phantom solid. Each therefore collides as 64
convex coacd pieces, built and wired into `so101.xml` by `build_jaw_collision.py` (re-run it to
change the settings; it also re-exports the `*_col.obj` the URDF's `<collision>` blocks point at).

Fidelity, measured as how far the collider surface protrudes past the true mesh surface:

| pieces/part | excess volume (jaw / finger) | mean error | p95 |
|---|---|---|---|
| 1 (bare hull) | 2.33x / 2.58x | — | — |
| 24 (previous) | 1.21x / 1.22x | 0.43 / 0.57 mm | 1.64 / 2.26 mm |
| **64 (current)** | **1.08x / 1.09x** | **0.26 / 0.41 mm** | **1.16 / 1.74 mm** |

Two things worth knowing before tuning this again:
- **`max_convex_hull` is the only knob that moves the error.** Threshold and voxel resolution are
  nearly inert (5x threshold and 4x resolution bought 1.212x -> 1.188x) because coacd's `merge`
  pass fuses the fine pieces back together regardless. `merge=False` reaches 1.011x but *ignores*
  the cap and emits ~350 pieces per part — too many to collide.
- **The ~5 mm worst-case protrusion is irreducible.** Both meshes are high genus (the moving jaw
  is genus 17: bolt bores, hinge bore, servo-horn interface) and convex pieces fill a bore by
  construction, so it survives even at 350 pieces. It sits at the mounting end, not the jaw tips.
  Removing it would need a non-convex collider (SDF), which MuJoCo does not support.

- **The build is not reproducible.** coacd's MCTS is multithreaded and ignores its `seed`, so
  re-running `build_jaw_collision.py` yields equivalent-but-different pieces — enough to flip a
  marginal scripted grasp between `success` and `off_center`. The committed STLs are the artifact
  of record; re-run the script only to change the settings, never to refresh the assets.

Cost of 24 -> 64: 74 -> ~80-96 us/step in plain MuJoCo through a scripted grasp, with max `ncon`
10 -> 11-14 and max `nefc` 63 -> 73-91.
